PRD — Aplikasi Pemesanan Kantin Multi-Tenant (referensi pemesanan website dimsum HAKA) Ringkasan Eksekutif Aplikasi pemesanan kantin berbasis web yang menghubungkan pengguna (pemesan) dengan tenant (penjual) dan admin pengelola. Pengguna dapat memesan makanan secara dine in atau take away dari beberapa tenant dalam satu kantin, memilih menu, melihat foto, dan membayar melalui QRIS statis milik tenant masing-masing. Admin mengelola data tenant, menu, dan konfirmasi pembayaran. Status pesanan diperbarui secara realtime. Aplikasi terdiri dari dua frontend terpisah (user dan admin) yang berbagi satu backend API dan satu database, dijalankan dalam satu monorepo. 2\. Tujuan & Non-Tujuan 2.1 Tujuan Menyediakan antarmuka pemesanan yang cepat, tanpa login wajib bagi pemesan. Mendukung pemesanan dari beberapa tenant sekaligus dalam satu sesi (dipecah menjadi order terpisah per tenant). Menampilkan QRIS statis per tenant saat checkout, dengan konfirmasi pembayaran manual oleh tenant. Memberikan tracker status pesanan realtime kepada pemesan. Menyediakan panel admin untuk mengelola tenant, menu, outlet, denah, dan konfirmasi pembayaran. Menjaga keamanan data melalui autentikasi berbasis role, validasi input, dan RLS database. 2.2 Non-Tujuan (untuk Versi 1\) Tidak mengintegrasikan payment gateway otomatis (Midtrans, Xendit, dll.). Pembayaran QRIS bersifat statis dan dikonfirmasi manual. Tidak mendukung login bagi pemesan umum. Login hanya untuk admin dan akun tenant. Tidak mendukung pembayaran non-QRIS (tunai, kartu) pada versi ini. Tidak menyediakan fitur chat antara pemesan dan tenant. Tidak menyediakan aplikasi mobile native. Fokus pada web responsif. 3\. Fitur (Feature Specification) Setiap fitur di bawah akan memiliki file MD tersendiri di docs/features/. 7.1 F-01 · Katalog Tenant & Menu Deskripsi: Pemesan melihat daftar tenant, tab untuk berpindah tenant, dan menu per tenant. Komponen: Tab tenant, grid menu, kartu menu (nama, foto, harga, tombol tambah). Kriteria terima: Pengguna dapat berpindah antar tenant tanpa reload. Menu yang is\_available \= false tidak dapat dipesan. Foto menu menggunakan lazy-loading. 7.2 F-02 · Keranjang & Checkout Deskripsi: Pemesan mengisi nama, memilih dine in atau take away, lalu checkout. Komponen: Form nama, toggle order type, ringkasan keranjang, tombol checkout. Aturan bisnis: Jika keranjang berisi item dari \>1 tenant, checkout memecah menjadi order terpisah per tenant. Nama pemesan wajib diisi (min 2 karakter). Kriteria terima: Checkout berhasil membuat order dan order\_code unik. Total per order dihitung dari subtotal item \+ pajak (jika ada). 7.3 F-03 · QRIS Statis per Tenant Deskripsi: Setelah checkout, pemesan melihat gambar QRIS milik tenant terkait dan instruksi pembayaran. Komponen: Gambar QRIS, nama merchant, nominal, tombol "Saya sudah bayar". Aturan bisnis: QRIS diambil dari tenants.qris\_image\_url. Tombol "Saya sudah bayar" mengubah payment\_status menjadi pending\_confirmation. Konfirmasi akhir dilakukan oleh tenant/admin di web admin. 7.4 F-04 · Tracker Pesanan (Realtime) Deskripsi: Pemesan melihat status pesanan yang diperbarui otomatis. Komponen: Timeline status, kode order, estimasi waktu (opsional). Kriteria terima: Perubahan status oleh tenant muncul di layar pemesan \<5 detik tanpa refresh. Pemesan hanya menerima perubahan order miliknya (dibatasi RLS \+ filter channel). 7.5 F-05 · Denah Kantin & Outlet Deskripsi: Menampilkan denah statis kantin dan outlet agar pemesan tahu lokasi tenant. Komponen: Gambar denah (Supabase Storage), penanda tenant (opsional pada V1). Kriteria terima: Denah dapat diperbarui oleh Admin Pengelola tanpa deploy ulang. 7.6 F-06 · Panel Admin — Manajemen Tenant Deskripsi: Admin Pengelola melakukan CRUD tenant, mengunggah QRIS, dan menetapkan akun tenant. Kriteria terima: Admin dapat mengunggah QRIS ke Supabase Storage (signed URL). Akun tenant hanya dapat mengakses data tenant sendiri (RLS \+ API filter). 7.7 F-07 · Panel Admin — Manajemen Menu Deskripsi: Tenant melakukan CRUD menu miliknya (nama, harga, foto, ketersediaan). Kriteria terima: Foto menu divalidasi (tipe, ukuran maks 2 MB). Perubahan langsung terlihat di web user setelah cache invalidated. 7.8 F-08 · Panel Admin — Konfirmasi Pembayaran & Status Order Deskripsi: Tenant melihat daftar order dengan status pending\_confirmation, mencocokkan mutasi, lalu menekan "Terima Pembayaran" atau "Tolak". Kriteria terima: Aksi konfirmasi mencatat payment\_confirmed\_by dan payment\_confirmed\_at (audit trail). Status order otomatis berubah ke diproses setelah pembayaran diterima. 7.9 F-09 · Autentikasi & Otorisasi Admin/Tenant Deskripsi: Login via Supabase Auth untuk admin dan tenant. RBAC dicek di middleware Express. Kriteria terima: Tenant tidak bisa mengakses endpoint admin pengelola (403). JWT diverifikasi di setiap request API. 8\. Keamanan 8.1 Kontrol Wajib Area	Kontrol Autentikasi	Supabase Auth JWT, verifikasi di Express middleware Otorisasi	RBAC di middleware, RLS di database Validasi Input	Zod schema di semua endpoint, shared di packages/shared Rate Limiting	Di endpoint publik (/orders, /menus) — mis. 60 req/menit per IP Upload File	Signed URL Supabase Storage, validasi MIME & ukuran Secret Management	.env tidak masuk repo, hanya .env.example Logging	Structured logging untuk aksi sensitif (konfirmasi bayar, ubah status) Header Keamanan	Helmet.js di Express (CSP, HSTS, X-Frame-Options) CORS	Allowlist origin web-user dan web-admin saja Audit Trail	payment\_confirmed\_by, payment\_confirmed\_at, updated\_at 8.2 Threat Model Ringkas Pemesan memalsukan konfirmasi pembayaran → konfirmasi hanya bisa lewat endpoint tenant dengan JWT valid. Tenant mengakses order tenant lain → filter di API \+ RLS. Spam order → rate limit \+ CAPTCHA (opsional V1.1). Upload file berbahaya → validasi MIME, ukuran, simpan di bucket terpisah, akses publik hanya untuk foto menu. Kebocoran QRIS → tidak masalah (statis, memang publik), tetapi pastikan tidak ada secret merchant di gambar. 9\.
